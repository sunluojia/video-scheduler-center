# TikTok 爬取方案

2026-11-19 定稿，同日按复核实验修订。依据是两份实测：[身份池最终方案](../../video-insight-pipeline/docs/identity-pool-final-2026-11-19.md)、[反爬实测](../../video-insight-pipeline/docs/antibot-tiktok-2026-11-19.md)。代码从已经跑通的 [`antibot/`](../../video-insight-pipeline/antibot/README.md) 改起。

**每台爬取设备自己养一小批“身份”。一个身份就是一个真 Chrome 的浏览器资料目录，用它预热出 Cookie 和 `tt_chain_token`。身份不绑线路：每次做事都向调度中心要一条采集线路，线路好坏由调度中心按爬取程序报告的结果判断。获取作品时，用身份的浏览器打开达人主页；下载时，先用某个身份读作品页拿到媒体地址，再带这个身份的 token 经下载线路下载。身份不够时程序自己补，快过期时自己刷新，坏了自己换，启动后基本不用管。**

调度中心这边的批次、派单、上传和线路分配都不变，只加两处：`crawled` 可以带达人资料（6.1 节，已实现）；侧栏加一个“账号池”菜单，查看各台设备的身份（6.3 节）。

## 1. 实测定下的规矩

| 规矩 | 实测 |
| --- | --- |
| Cookie 只能由真浏览器拿到 | 纯 HTTP 换了 6 种 TLS 指纹，都只拿到约 1.4 KB 的 `Please wait...` 挑战页，一个 Cookie 也没有；真 Chrome 一次通过 |
| 成败看出口，不看身份 | 香港出口只有挑战页；本地宽带直连 TikTok 不通；机房 IP 连续压测后一直返回空内容（`200` 但 0 字节）。新旧资料目录 × 两条出口做 2×2：美国节点上新旧目录都是 0 条，大阪机房上分别是 32 条和 16 条，差别全在出口 |
| 作品列表由页面自己请求 | 页面自己发的请求 16/21 成功；自己拼参数或重放，30 次只成 1 次 |
| 下载只认 `tt_chain_token`，不认 IP | 同一地址换三条不同出口，下载的字节完全一致；只带 `tt_chain_token` 就能下，不带就 `403` |
| token 必须来自取到这条地址的那个身份 | 两个身份各取一次地址，交叉下载：自己的地址配自己的 token 是 `200`，配别人的 token 是 `403` |
| 下载取地址不用开浏览器 | `curl_cffi` 带身份的 Cookie 读作品页：`200`、427,207 字节，页面数据里有 `playAddr`、`downloadAddr` 和 4 档码率；用这个地址配同一身份的 token 下载是 `200` |
| 读完第一页往往就能结算 | 作品列表（`/api/post/item_list/`）跨页严格按发布时间倒序；置顶作品只出现在第一页，带 `isPinnedItem: true`，后面不再重复；第一次请求 `cursor=0`，之后每次用上一页返回的 `cursor`。第一次请求偶尔返回空内容（`200` 但 0 字节），要重新加载 |
| 账号和作品不存在有明确的码 | 页面数据里 `webapp.user-detail.statusCode` 为 10221（“user banned”）表示账号不存在；`webapp.video-detail.statusCode` 为 10204（“item doesn't exist”）表示作品没了 |

早先“复用资料目录 7/8、每次新开 0/8”的对比，用上面的 2×2 复核后看是出口造成的，不再当作规矩。资料目录照旧复用，因为不花成本，Cookie 也从它来。

## 2. 整体流程

```
crawl_creator
  挑一个身份，要一条采集线路 → 用身份的浏览器打开达人主页
  → 从页面数据读资料 → 抓页面自己加载的作品列表 → 选出前五条 → 回传 crawled

调度中心锁定清单，每条视频发一个 download_video

download_video（一次尝试）
  要一条下载线路 → 挑一个身份，要一条采集线路，带身份的 Cookie 读作品页，拿到媒体地址
  → 带同一个身份的 token 经下载线路下载 → 校验 → 上传
```

两种线路的说法：**采集线路**是调度中心“获取信息”用途的线路，**下载线路**是“下载视频”用途的线路。两者怎么分配、怎么判好坏，见[代理方案](proxy-design.md)。

## 3. 身份池

### 3.1 放在哪、存什么

- 身份池是爬取程序里的一个模块，不是单独的服务。每台设备只跑一个爬取进程，身份由这个进程管理。
- 浏览器资料目录在本机磁盘上，所以身份只在本机使用。下载任务落到哪台设备，就用那台设备的身份取地址，地址和 token 在同一次尝试里配对使用，不跨设备，也不跨尝试。
- 资料目录放在 `CRAWLER_PROFILE_ROOT` 下，一个身份一个目录。目录里有 Cookie，按密码对待：不进仓库，只允许运行爬取程序的系统账号读写，退休时直接删除。目录里只有匿名访客的 Cookie，没有登录账号，不需要安全擦除。
- Cookie 和 token 只放在内存里，不写数据库。程序重启后，按已有目录把身份重新预热一遍，约 7 秒一个。这样不用加密，也不用管密钥。
- 本地状态表只记身份的基本信息：目录、状态、连续失败次数、冷却到期时间、最近使用时间、预热时间、浏览器版本。

### 3.2 后台循环：补充和刷新

「执行程序」按设备设置同时预热的身份数，默认 1，随心跳下发。每个预热任务独占一个浏览器资料目录，并申请一条「获取信息」线路。成功后该名额可以立即开始下一次。失败后至少等待 12 秒，分不到线路时还要等够调度中心给出的时间。降低并发时已开始的任务继续运行。

低于本机目标时，优先恢复未冷却、会话无效且仍计入目标的身份，再按缺口新建。正在预热的身份预占目标名额。总数达到目标的两倍时，冷却结束的旧身份仍可恢复。可用数量达到目标后，再处理其他到期的身份和满 25 分钟的提前刷新。

预热（新建和刷新相同）：

1. 按“获取信息”用途向调度中心申请一条采集线路，带上次预热失败的线路（`avoid`）。
2. 用 patchright 以这个目录启动本机 Chrome（`channel="chrome"`，预热默认无头），经本机转发口走这条线路（第 8 节）。
3. 打开 `https://www.tiktok.com/`，等页面数据 `#__UNIVERSAL_DATA_FOR_REHYDRATION__` 出现，最多 45 秒。
4. 读出 Cookie。`tt_chain_token` 不为空才算成功，同时记下 User-Agent。关闭浏览器，目录留在磁盘上。
5. 归还线路：成功报“正常”，停在挑战页或拿不到 token 报“可疑”。

预热失败不计入连续被拒次数。已有资料预热失败后至少等 60 秒再试，其他身份可以先预热。新建失败的直接删掉目录。

### 3.3 挑身份

- 只挑能用的身份：没在冷却、没被占用、有 token 且没过期、浏览器版本和本机 Chrome 一致。
- 连续失败少的优先；一样少的，挑最久没用的，大家轮着用。
- 一个身份同一时间只做一件事。同一个资料目录只能被一个 Chrome 打开；每台设备最多同时做 6 件事（获取作品 2 + 下载 4），8 个身份够用。
- 先挑身份，再向调度中心要采集线路，带上这个任务失败过的线路（`avoid`）。要不到线路就把身份放回去，按调度中心给的时间再来。
- 一个身份也挑不出来：任务 10 秒后再挑。这算环境问题，不算失败，也不算尝试次数。

### 3.4 身份的好坏

| 结果 | 身份怎么变 |
| --- | --- |
| 成功 | 连续失败清零 |
| 内容本身的结论：账号私密、不存在、作品已删 | 不变 |
| 下载 `403` | 连续失败加 1，进入冷却：60 秒起，每次翻倍，最长 30 分钟。token 作废，由后台重新预热 |
| 空正文、正文读取失败、挑战页、预热拿不到 token、超时、断开 | 不变。任务和线路的处理见第 6.2 节和第 7 节。 |

- 连续失败 3 次及以上，不再计入“可用身份”，后台会先补一个新的。它冷却结束后仍然可以被挑中，只是排在后面。
- 连续失败 6 次（这时冷却已经到 30 分钟上限）：退休，删掉目录，状态表里留一行记录。
- 本机 Chrome 升级或换浏览器后，旧身份全部退休重建，因为 token 只对签发它的浏览器会话有效。

## 4. 获取资料和最新作品（`crawl_creator`）

1. 挑一个身份，要一条采集线路，用它的目录启动 Chrome。
2. 先开始监听页面响应，再打开 `https://www.tiktok.com/@{handle}`。
3. 从页面数据 `webapp.user-detail` 里读资料：平台用户 ID、`uniqueId`、昵称、`secUid`、是否私密。`uniqueId` 要和任务里的账号一致。确认私密或不存在就结束。
4. 抓页面自己发出的 `/api/post/item_list/` 的响应，一页约 16 条。要下一页时滚动页面，让页面自己去加载。
5. HTTP 200 空正文在同一次尝试里最多恢复一次。首屏空正文刷新一次，后续页空正文滚动一次。正文读取失败、格式错误、两次连续等待响应超时都按任务退避。
6. 按第 7 节选片、结算。图文按 `photo` 占位。成功的末页可以没有作品，结果为空列表。
7. 关闭浏览器前再读一次 Cookie，更新这个身份的 token，相当于顺带刷新。
8. 归还线路。

读取列表阶段最多 30 秒、10 页。采集并发在「执行程序」页按设备配置。

## 5. 下载一条视频（`download_video`）

整体沿用[单视频下载方案](video-download-design.md)：按“尝试”进行，失败后让出名额，稍后再试，校验、落盘、上传、重启恢复的规则都不变。一次尝试的前几步改成：

1. **要下载线路**：按“下载视频”用途申请。申请不到就不开始。
2. **取地址**：挑一个身份，要一条采集线路。带这个身份的 Cookie 和 User-Agent，用 `curl_cffi`（Chrome 指纹）读任务里的作品页，从页面数据 `webapp.video-detail` 取地址候选，按 `playAddr`、`bitrateInfo[].PlayAddr`、`downloadAddr` 的顺序。只有拿到挑战页或没有页面数据时，才用这个身份的浏览器打开作品页再读。读完立即归还采集线路。
3. **下载**：经下载线路发请求，请求头带同一个身份的 User-Agent、`Cookie: tt_chain_token=…` 和 `Referer: 作品页`。
4. 下载结果同时记到身份上（3.4 节）和下载线路上（第 7 节表格）。

地址和身份只在这一次尝试里成对使用，不入库。下一次尝试重新挑身份，重新取地址。

**取地址优先**：采集线路由获取作品和下载取地址共用。设备上有下载在等采集线路时，先不开始新的获取作品，免得批量采集把下载饿住。取地址只占线路一两秒，获取作品要占几十秒，让一下影响很小。

`403` 先排除自己的问题，顺序不能颠倒：token 是不是取地址的那个身份的（代码保证）→ Referer 是不是作品页（代码保证）→ 地址是否过期 → 最后才是线路。

## 6. 和调度中心的约定

任务、事件、上传、心跳、暂停和取消都按[设计文档第 4 节](design.md#4-与爬取程序的约定)，不变。新增和需要注意的：

### 6.1 `crawled` 带上达人资料（已实现）

`crawled` 可以带 `profile`：`handle`、`url` 必填，`nickname`、`platform_user_id` 读不到可以为空。任何结论都可以带，私密账号也能回传昵称。调度中心保存最近一次回传的资料，在达人详情的“平台资料”里显示；名单里的账号和 `creator_oecuid` 保持原值。模拟爬取程序已经按这个格式回传。

### 6.2 列表读取结果与线路状态

采集程序归还线路时，用 `listing_result` 区分完整列表、重复空正文和任务读取异常，原因随租约一起保存。读取异常按任务退避。短时重复空正文按近期跨任务证据决定是否暂停分配。完整列表可以清除此前的空正文证据。限流和代理连接失败分别按 `Retry-After` 和独立的代理端口复查结果处理。规则见[代理方案](proxy-design.md#4-线路好坏怎么判)。

### 6.3 “账号池”菜单（已实现）

调度中心侧栏在“代理”下面加一个“账号池”菜单，集中查看各台设备的身份。账号池里每一项是一个浏览器身份，即未登录的访客，不是平台账号。

**数据从哪来**：爬取程序每 15 秒的心跳带上本机身份池的快照，调度中心按设备保存最近一份。心跳本来就带着正在用的线路，这里是同样的做法。设备离线后，页面仍显示它最后的样子，并标为“离线”。Cookie 和 token 不进快照，仍然只在设备上。

快照内容：

- **汇总**：目标可用数、可用数、使用中、预热中、冷却中、总数，可用数从什么时候开始低于目标；最近一小时的预热次数和失败次数、作品列表请求数和空内容数、下载次数和 `403` 次数。可用指有没过期的 token、不在冷却，正在用的也算；只看 token，是因为采集线路坏了时预热会一直失败，身份都在却都没 token，这时要提示。
- **每个身份**：编号（资料目录名）、状态（可用、使用中、预热中、冷却中、待预热、已退休；待预热是 token 过期或重启后还没预热）、连续失败次数、冷却到期时间、token 到期时间、最近使用时间、预热时间、浏览器版本。已退休的只带最近 24 小时内的、最多 20 个，附退休原因。

**页面**，布局和“代理”页一致：

- **顶部**：需要人处理的问题。某台设备的可用身份低于目标超过 10 分钟就提示，同时给出最近一小时的预热成功率，方便判断是不是采集线路的问题。和代理的问题一样，也显示在“执行程序”页顶部，侧栏“账号池”旁显示条数。
- **设备卡片**：每台设备一张，显示在线状态、可用数 / 目标数、预热中、冷却中，以及最近一小时的三个比率。
- **身份表**：可以按设备、状态筛选，默认不显示已退休的。每行两个操作：
  - **刷新**：立即重新预热这个身份。
  - **退休**：删掉它的资料目录，后台会自动补一个新的。

  操作由调度中心转给那台设备执行，设备离线时按钮不可用；页面在下一次心跳后更新。

**账号池数量**：页面右上角的按钮设置“至少保持几个可用”（默认 8 个），存在调度中心。爬取程序每次心跳，调度中心在回复里告诉它分到几个：总数按在线的爬取程序平均分摊，向上取整；一台离线，其余的下一次心跳就多分一些。爬取程序按分到的数量自动补充：可用的少于这个数就新建并预热，快过期的刷新，连续被拒的换掉；每台最多留分到数量的两倍（不计入的还占着位置，退休后再补）。调低不删已有的身份，只是不再补。爬取程序本身不再配置身份数量。

**页面上不放的**：Cookie 明文、启动和停止按钮。身份池随爬取程序启动，一直运行。

| 接口 | 用途 |
| --- | --- |
| `PUT /api/crawler-services/{instance_id}` | 注册和心跳，请求体的 `identities` 带上上面的快照。回复 `{"identity_target": 分到的可用数, "crawl_slots": …, "download_slots": …, "warm_slots": …}`，并发见第 8 节。 |
| `GET /api/identities` | 页面接口：账号池数量、各设备的汇总、身份列表和需要人处理的问题 |
| `PUT /api/identity-pool` | 页面接口：设置账号池至少保持几个可用，`{"target": 8}` |
| `POST /api/identities/{instance_id}/{identity_id}/{action}` | 页面接口：`action` 取 `refresh` 刷新或 `retire` 退休，由调度中心转给那台设备 |
| 爬取程序新增 `POST /api/identities/{identity_id}/{action}` | 同上，设备这一侧执行，要求服务凭据 |

### 6.4 沿用的做法

- 只消费 `crawler.tasks`，Dramatiq Worker 要限定 `--queues crawler.tasks`。
- 收到任务先记进本地状态表，再回 `accepted`。按 `task_id + run` 去重，更大的轮次取代旧轮次。待发事件也记在表里，补发时沿用原来的 `event_id`。
- 下载完成就上传：`204` 后清理本地文件；`422` 复核文件后按尝试次数重试；`404`、`409` 丢弃文件，不再重试。
- 暂停只是不开始新的尝试；取消记进本地状态，迟到的任务也会被拦下。

## 7. 选片、结论和失败归类

**选片**：

- 按平台作品 ID 去重，ID 按字符串保存。发布时间换算成 UTC，`published_at <= cutoff` 才入选。
- 按发布时间倒序，同一秒按作品 ID 的数值倒序。置顶作品按原发布时间排。图文和视频一起取前五。
- 读到列表末页就可以结算。列表顺序和置顶标记经实测确认后（第 10 节第 1 条），读到一条严格早于第 5 名的普通作品也可以结算，同一秒的继续读。
- 游标重复、缺页、10 页读完还不能确定前五，本次尝试失败。

**结论**：

- 确认私密或不存在：`private`、`not_found`。
- 确认是公开账号，截止时间前没有作品：`ok` 和空清单。
- 其他情况：本次尝试失败。一个任务最多尝试 3 次，每次带上失败过的线路，换线路也换身份；3 次都失败回 `failed`，带最后一次的原因。等线路、等身份不算尝试次数，环境恢复后自己接着跑，和下载的规则一致。

**失败归类**（身份怎么变见 3.4 节，线路的五种表现见代理方案第 4 节）：

| 看到的情况 | 身份 | 线路 | 这个任务 |
| --- | --- | --- | --- |
| 拿到数据、文件完整 | 成功 | 正常 | 继续 |
| 账号私密或不存在，作品已删 | 不变 | 正常 | 按结论结束 |
| 读作品页拿到挑战页或没有页面数据 | 不变 | 正常 | 改用这个身份的浏览器再读 |
| 浏览器也停在挑战页 | 不变 | 可疑 | 换线路重试 |
| 作品列表两次返回 HTTP 200 空正文 | 不变 | 记空正文，按跨任务证据判断是否短暂停用 | 任务退避 |
| 作品列表正文读取失败、格式错误、等待超时 | 不变 | 记录读取异常 | 任务退避 |
| 下载 `403` | 连续失败加 1，token 作废 | 可疑 | 稍后换身份、换线路重试 |
| 连接超时、中途断开 | 不变 | 可疑；代理复测仍不通就报“代理不通” | 重试 |
| `407`、代理认证失败 | 不变 | 认证失败 | 等环境恢复 |
| `429` | 不变 | 限流，带 `Retry-After` | 等环境恢复 |
| 申请不到线路、没有可用身份 | 不变 | — | 等，不算次数 |

## 8. 部署

- **采集线路**：“获取信息”用途走代理池，限定在一个“美国住宅”文件夹里。住宅代理按粘性会话登记，每个会话一个代理（用户名里带会话号）。不要香港出口；本地宽带直连 TikTok 不通。开发库现在把“获取信息”设成了直连，接真实爬取程序前要改。
- **下载线路**：什么出口都行，机房 IP 也能下。现在的“SSH 加密代理”实测 4 并发 42 Mbit/s，够用。
- **浏览器不直接连带口令的代理**：Playwright 把带口令的 HTTP 代理交给 Chrome 会报 `ERR_INVALID_AUTH_CREDENTIALS`，带口令的 SOCKS5 直接报 `ERR_NO_SUPPORTED_PROXIES`，VPS 隧道也一样。所以浏览器每次启动，都在本机开一个无口令的转发口给它用：
  - 监听端口填 0，由系统分配，浏览器关闭时一起关掉，不需要端口池。
  - `antibot/forward.py` 的 `Forwarder` 已经有启动和停止，改成跟着浏览器开关；按固定端口复用的 `ensure_forwarder` 不再用。还要补上 SSH。
  - `curl_cffi` 和下载直接连代理；SSH 线路不管谁用，都经转发口。
- **浏览器**：本机装 Chrome，patchright 用 `channel="chrome"`、有界面。Linux 上要配虚拟显示，例如 Xvfb。一个 Chrome 约 400 MB。patchright 出问题（比如和新版 Chrome 不兼容）时，换回原版 Playwright：接口相同，实测原版 Playwright 打开真 Chrome 也能通过挑战，只是自动化痕迹多一些。

**每台设备的初值**：

| 项目 | 初值 |
| --- | --- |
| 身份 | 账号池至少保持 8 个可用（多台设备平均分摊），每台最多留分到数量的两倍。每个预热名额两次尝试至少间隔 12 秒，满 25 分钟刷新。 |
| 浏览器 | 采集、下载和预热并发在「执行程序」页按设备设置，默认分别为 2、4 和 1，随心跳下发。Chrome 数量上限是采集并发加预热并发，下载回退到浏览器时也使用该名额。 |
| 获取作品 | 列表阶段最多 30 秒、10 页。普通任务失败最多尝试 3 次。 |
| 下载 | 同时 4 次尝试，不开浏览器；其余见单视频下载方案第 7 节 |
| 线路 | 采集和下载的每条线路同时最多 2 个，由调度中心在整个集群范围内控制 |

**容量粗估**（按单次实测推算，上线后以批次的实际进度为准）：

| 环节 | 算法 | 每小时 |
| --- | --- | --- |
| 一条采集线路 | 获取作品约 20 秒（含启动浏览器和偶尔的空内容重试），加上取地址约 2 秒 × 平均 4 条视频，一位达人约占 28 秒；同时 2 个 | 约 250 位达人 |
| 一条下载线路 | 每条视频平均约 7.5 MB，一位达人约 30 MB；同时 2 个约 30 Mbit/s，一位达人约 8 秒 | 约 450 位达人 |
| 一台设备 | 同时 2 个获取作品，每个约 20 秒；下载不开浏览器，不是瓶颈 | 约 360 位达人 |

现在一台设备、一条采集线路、一条下载线路，每小时约 250 位达人，瓶颈是采集线路。先加采集线路；一台设备约 1.5 条采集线路就用满，再往上就加设备。

## 9. 和之前方案的不同

和本文档上一版、[视频获取方案](video-acquisition-design.md)相比：

| 之前 | 现在 | 原因 |
| --- | --- | --- |
| Camoufox + Playwright，每次新建上下文 | patchright + 本机 Chrome，复用身份目录 | Chrome 已跑通，Camoufox 本机没装；复用目录不花成本 |
| 同时对测 DTK API | 首期不接 | DTK 的身份是生成的访客 Cookie，身份池空了直接失败，下载直连不走代理，三处都和实测不符 |
| 取地址和下载用同一条线路、同一会话 | 取地址用任一采集线路，下载走下载线路，带同一身份的 token | 下载只认 token，不认 IP |
| 获取作品共用 5 分钟预算 | 最多尝试 3 次，等线路、等身份不算 | 和下载一致，环境恢复后自己接着跑 |

和[身份池最终方案](../../video-insight-pipeline/docs/identity-pool-final-2026-11-19.md)相比，做了这些简化和修正：

| 身份池方案 | 本方案 | 原因 |
| --- | --- | --- |
| 身份和采集出口强制配对，不重组 | 身份不绑线路，每次向调度中心要 | 2×2 复核：同一出口上新旧资料目录结果一样，成败全在出口。绑死的话，一条线路变差，上面的身份一起废掉 |
| 空内容按半次风控记到身份上；代理挂了，身上的身份一起冷却 | 空内容、挑战页、网络问题只记在线路上 | 同上；线路好坏以调度中心为准 |
| 单独的身份池服务，有申请、归还接口和租约表 | 爬取程序里的模块，用内存标记“正在用” | 身份只在本机、同一进程里用，重启时“正在用”自然清空 |
| Cookie、token 加密入库（Fernet，附加数据绑身份 ID） | 只放内存，重启后重新预热 | token 30 分钟就要刷新，存库意义不大；而且 Fernet 不支持附加数据 |
| 健康分（成功率 × 风控率 × 0.5 的连续失败次方），分 5 档轮换 | 连续失败少的优先，再按最久没用 | 每台设备只有 8 个左右身份，用不上分档；身份多了再加 |
| “降级考察期”状态 | 连续失败 3 次不计入可用，6 次退休 | 新建一个身份只要 7 秒，不值得专门养考察期 |
| 读资料单独走 HTTP | 获取作品时，同一次浏览器访问顺带读资料；HTTP + Cookie 用在下载取地址 | `crawl_creator` 反正要开浏览器；HTTP 读作品页已实测可行 |
| 按钮启动、停止、补货，能查看明文 Cookie | 随爬取程序启动，一直运行；在调度中心“账号池”菜单查看，可以刷新、退休单个身份；不提供明文 Cookie | 启动后不用管；Cookie 等同密码 |
| 过滤图文作品 | 图文按 `photo` 占位 | 调度中心的规则：图文和视频一起数前五 |
| 下载后用 ffprobe、ffmpeg 全片解码校验 | 只校验传输完整（单视频下载方案第 2 节） | 媒体是否有效由分析服务判断，爬取程序不重复做 |
| 一页结论里写 `use=downloader.download_video` | `crawler.download_video` | 调度中心实际的用途名，原文第 2.7 节也是这个 |

旧爬虫里去掉的兜底（不变）：

| 旧逻辑 | 现在 |
| --- | --- |
| 用哼哼猫的标题、点赞、播放量和音频猜作品 | 只用平台作品 ID、作者和发布时间 |
| 自动换 VPN、跨渠道补采、多层自检、连续十人失败自动停批 | 按单个达人或单条视频回传原始原因，暂停和补跑由调度中心控制 |

## 12. 验收

- **冷启动**：资料目录为空时启动，2 分钟内可用身份达到 8 个，“账号池”页能看到。
- **账号池页面**：在页面上退休一个身份，下一次心跳后它显示为已退休，后台补上一个新的；设备离线后页面标为离线，按钮不可用；可用身份低于目标超过 10 分钟时顶部出现提示。
- **重启**后先按设备的并发设置重新预热已有目录，再补足可用身份目标。
- **端到端**：至少 3 位达人，覆盖图文混排、置顶和需要翻页的情况；资料、前五条、下载、上传全部完成，作品 ID、类型、顺位和发布时间核对一致。
- **token 配对**：每次下载用的 token 都来自取地址的那个身份（日志可查）；故意换成别的身份的 token 应该得到 `403`。
- **线路变差**：一条采集线路开始只给空内容，几次之后调度中心把它冷却，任务换线路继续，身份的连续失败次数不变。所有采集线路停用时，任务等待不失败，恢复后自己继续。
- **取地址优先**：获取作品占满采集线路时，下载的取地址仍能在下一个空位拿到线路。
- **换浏览器**：Chrome 升级后旧身份全部退休重建。
- **资源**：同时开的 Chrome 不超过 3 个；浏览器关闭后它的转发口也关了。
- **图文**：混排的达人里图文保留位置，调度中心只给视频派下载。
